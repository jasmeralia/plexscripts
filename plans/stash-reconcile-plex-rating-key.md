# Design: store the Plex rating key on Stash scenes during reconcile

## Goal

After `plexadm stash reconcile`, a Stash scene that matches a Plex video by file path should expose that video's Plex `ratingKey`. This makes a Stash-to-Plex lookup possible without rescanning and joining both libraries' file paths. A Plex merge should update the surviving Stash scene to the surviving Plex rating key on the next reconcile run.

This document describes the implementation; it does not change reconcile behavior yet.

## Current behavior and supported storage

On current `master`, `plexadm/stash_reconcile.py` optionally scans Stash, then runs Stash Clean only for a full Plex-library run. Runs scoped by `--limit`, `--added-in-last-days`, or `--path` skip Clean because it affects the entire Stash library. Reconcile then indexes scenes by file path and matches Plex video locations to that index. One matched scene receives `sceneUpdate`; multiple matched scenes are combined with `sceneMerge`, with the lowest numeric Stash scene ID as the destination. A Plex video with no usable descriptive metadata is recorded in the scope CSV and receives no Stash metadata update. `plexadm/stash.py` currently requests no scene identifier field that could hold a Plex key.

The running Stash instance reports version `v0.31.1`. Its GraphQL schema exposes `Scene.custom_fields: Map!` and `SceneUpdateInput.custom_fields: CustomFieldsInput`; `CustomFieldsInput.partial` updates only named keys, while `full` replaces the entire map. `SceneFilterType.custom_fields` accepts field criteria, so this field can support a direct Stash query. Check schema support at startup or document `v0.31.1` as the minimum supported Stash version for this feature.

Use a single namespaced custom field, `plex_rating_key`, containing the decimal `ratingKey` as a **string**. Plex IDs identify records within one Plex server, which matches this tool's configured single-server model. The key can change if Plex replaces an item; it is a lookup hint maintained by reconcile, not a permanent identity for the media file. If multiple Plex servers are supported later, add server identity before treating the key as globally unique.

Do not use Stash `stash_ids`: those identify entities on Stash-box endpoints. `code`, `details`, and `urls` have user-facing scene metadata meanings and could overwrite unrelated values. The partial custom-field update preserves other custom fields.

Treat `plex_rating_key` as a field reserved and owned by plexadm. Reconcile may set or remove this one key, but must preserve unrelated custom fields and must never replace the full custom-field map.

## Reconcile flow

1. Keep the existing `_FIND_SCENES` query and `all_scenes()` path-to-scene return contract unchanged for their current callers. Add a reconcile-specific complete-inventory query/method that selects `custom_fields` while retaining the full scene shape the current reconcile loop uses, including `performers` and `tags`, plus file paths. Its collection must retain scenes with `files` equal to `null` or an empty list and must not collapse scenes that share a file path. Validate pagination by comparing the independently reported `findScenes.count` with the number of unique scene IDs collected; an empty/short page before the reported count, duplicate IDs, or count mismatch makes the inventory incomplete and aborts reconciliation before cleanup. Build the reconcile path index from this complete collection, preserving every scene associated with a path; do not use the legacy lossy path-to-single-scene map as the cleanup inventory. This keeps sync-tags, backfill-tags, and inventory callers from acquiring a new custom-field schema dependency, and prevents reconciliation from dropping existing performer/tag memberships.
2. After the Plex video list is loaded, perform a read-only planning pass. For partial scopes (`--limit`, `--path`, or `--added-in-last-days`), load the full Plex video inventory for ambiguity validation while using only the selected subset to decide which videos receive the requested reconcile work. Treat the reloaded full inventory as authoritative and verify its count against the Plex section's independently reported `totalSize`; a missing total or count mismatch aborts before per-video changes. Do not issue one `reload()` request per video. Hydrate the full records with bounded batches using PlexAPI `PlexObject.fetchItems` with lists of rating keys, validate that every requested identity appears exactly once, and cap batches at 100 items. For the rare record without a usable `ratingKey`, fetch its stable Plex item URI through the bounded fallback path. This keeps request count proportional to batches rather than library size while providing `locations` and complete scene data for global ambiguity checks. Full-inventory hydration is a deliberate cost of global ambiguity validation even on `--limit` and `--added-in-last-days` runs; report progress during it and include a large-library performance acceptance check before implementation is considered ready. `--path` already reloads every item in the current command before applying its path filter. Assign a canonical run-local identity to each hydrated full-inventory item and map the selected query results to exactly one such item, first by normalized decimal `ratingKey`, then by stable item URI when the key is missing or invalid. Do not use Python object identity or shared file paths as fallback identities. If a batch request fails, returns duplicate/missing records, or a selected result cannot be mapped uniquely, abort before per-video Stash entity creation, scene mutation, or stale-key cleanup. A missing or invalid `ratingKey` still counts as an item identity and retains its path matches, but skips its key write. A `locations` attribute that is present with an empty list is valid: it means the Plex item currently has no file paths, so it contributes no Stash path matches. Abort only when the full item data omits the `locations` attribute or cannot otherwise be validated. Record every path match from the full inventory in a `path_matched_scene_ids` set and the distinct canonical Plex item identities matched to each Stash scene. A scene matched to more than one Plex item is ambiguous even if only one item has a valid key; report it and exclude every planned write and merge involving that scene. Finish matching and ambiguity validation for the entire inventory before resolving or creating metadata entities. Stash Scan and full-run Clean happen before this planning pass and may already have changed Stash when later Plex validation fails; those operations are not rolled back.
3. After canonicalization, use the reloaded full-inventory record as the authoritative source for `ratingKey`, `locations`, and other Plex fields used by planning or reconciliation; the selected query result supplies only the identity needed to find that record. Normalize the canonical record's `ratingKey` to a nonempty decimal string before planning a key write. Report and skip key writes for canonical records with an absent or invalid key, but retain their path matches. For a uniquely matched scene, remove any existing `plex_rating_key` because it cannot describe the current path-matched item; ambiguous scenes remain untouched. When a video has a unique, non-ambiguous scene match, existing non-key reconciliation may continue under its current metadata rules, while the invalid key itself is not written. Keep the planning pass read-only: do not call `find_or_create_studio`, `find_or_create_performer`, `find_or_create_tag`, or any other mutating resolver while planning. Begin the apply phase only after the recovery-artifact preflight in step 4 has completed. Then resolve/create entities only for validated, non-ambiguous planned operations and perform the corresponding scene update or merge. For a uniquely matched scene whose canonical Plex item has a missing or invalid `ratingKey`, schedule removal of any existing `plex_rating_key` instead of leaving a potentially stale key attached to the new file; never clear it for an ambiguous scene. For an ordinary one-scene match with a valid canonical key, include `custom_fields: {partial: {plex_rating_key: key}}` in the existing `sceneUpdate` input. For a video with no usable descriptive metadata, issue a field-only `sceneUpdate` for **each** matched scene whose key is missing or different; keep those scenes in the existing `matched_no_data` scope count. Avoid an extra field-only call when the stored key already matches. This leaves the current no-metadata merge gate intact, so several Stash scenes can temporarily hold the same Plex key.
4. At command startup, run the read-only schema preflight, resolve the reference directory, and acquire an exclusive process lock at `${reference_dir}/stash-reconcile-merge-recovery.lock` before any Stash mutation. Hold it through recovery, Scan/Clean, planning, apply, and cleanup so a second reconcile cannot build a stale plan or race the active run; a competing invocation must wait or fail before Stash work begins. Before Scan/Clean, recover any active artifact. If recovery cannot safely complete, abort the run before Scan/Clean. Also load every valid record from `stash-reconcile-merge-quarantine/` and exclude all recorded scene IDs from merges and key cleanup on every run; warn with the quarantine file path and blocked IDs. If any unresolved quarantine record exists, skip full-library `stash.clean()` because Clean could delete a quarantined source whose file is still missing; report that Clean was skipped. An operator removes a quarantine record only after restoring/validating its saved custom fields and confirming which surviving scene should own the Plex key. Then, after the read-only plan is complete and before entering apply (including any mutating studio/performer/tag resolver), persist a recovery artifact for all planned multi-scene merges. Resolve its directory in Python with this precedence: use `PLEXADM_REFERENCE_DIR` when set; otherwise use the repository-root `reference/` directory when running from a checkout where it exists; otherwise use `/usr/local/share/plexadm/reference`, matching the installed `mass_process.sh` fallback. Update `mass_process.sh` to export its resolved `PLEXADM_REFERENCE_DIR` so the report/review outputs and reconcile recovery artifact share the same directory. Never use a current-working-directory-relative fallback. Use one fixed active filename, `stash-reconcile-merge-recovery.json`, written only while holding that whole-run process lock; never replace an existing active artifact with a new run's plan. Write it with mode `0600`, via a temporary file, `fsync`, atomic rename, and parent-directory `fsync`. It contains destination/source scene IDs, complete pre-merge custom-field maps, intended target `plex_rating_key`, and a pending/completed state per merge, with no titles or paths; it remains local and ignored by Git. If it cannot be durably written, abort the per-video apply phase before any resolver, entity creation, scene/key mutation, merge, or stale-key cleanup (the already completed Scan/Clean remains as described above). The durable snapshot must be updated atomically and synced after each successfully restored merge. If the process restarts with an active artifact, recover it before planning or applying any new merges. Recovery must inspect current scene IDs and never repeat `sceneMerge` when the recorded source scenes are already gone; in that case, restore and verify the saved custom fields and target key on the surviving destination, then mark that entry complete. If any recorded source remains, recovery may retry only the still-unmerged sources after validating that the destination and source data are present. If the recorded destination is missing, atomically move the artifact into `${reference_dir}/stash-reconcile-merge-quarantine/`, preserve its full snapshot, and emit a prominent error with all affected scene IDs. Continue unrelated reconcile work, but exclude those IDs from future merges and stale-key cleanup using the quarantine records loaded at every startup; do not let one missing destination block the whole library indefinitely. Retain the active artifact on merge or restore failure; remove it only after every merge has been confirmed restored. Exclude the plexadm-owned `plex_rating_key` while building the union of non-owned fields. If two scenes have the same non-owned field with different values, do not merge that group; leave its scenes intact, update each scene independently with the planned Plex metadata and target key using partial custom-field updates, and report the field conflict for review. For a conflict-free group, include the union of non-owned fields plus the target `plex_rating_key` in `sceneMerge.values.custom_fields.partial`, so the merge call itself applies the intended custom-field state to the destination. After `sceneMerge` succeeds, read the destination back, verify the complete field map, and reapply with `custom_fields.partial` if needed. Confirm the final state before marking the merge complete; retain the durable pre-merge artifact so a crash between the merge and readback can still recover. Verify these recovery states and Stash's actual merge behavior in integration coverage, including that `sceneMerge.values.custom_fields.partial` applies the field union to the destination.
5. Only after a successful **full** Plex scan, a verified complete Plex inventory, and completion of the validated update/merge plan, remove `plex_rating_key` from scenes absent from `path_matched_scene_ids` that currently contain that key, using `custom_fields: {remove: ["plex_rating_key"]}`. The full Plex inventory count must equal the library section's independently reported `totalSize`; missing totals or count mismatches abort before per-video mutations and cleanup. If both report zero videos, do not remove any keys: warn and skip orphan cleanup unless a future explicit operator opt-in is added for an intentionally empty library. Determine path matches independently of key validation: a scene matched to a Plex video with a missing or invalid key is excluded from unmatched-scene cleanup, but a separate planned invalid-key clear removes any old key from that uniquely matched scene. Do not issue a removal mutation for a scene without the key, and count only keys actually removed. Use the complete scene collection for this comparison, including fileless scenes and scenes omitted by a single-value path index; determine path matches without losing scenes that share a path. Do not clear unmatched keys on runs limited by `--limit`, `--added-in-last-days`, or `--path`; a selected, uniquely path-matched invalid-key scene may have its stale key cleared after the same full ambiguity validation. Never clear unrelated custom fields. On current `master`, a full run performs Stash Clean before building the scene inventory; partial runs skip Clean. This design skips full-run Clean while unresolved quarantine records exist, so their source scenes remain available for operator recovery. Stale-key cleanup handles surviving Stash scenes that have no Plex path match.
6. Print counts for keys added, changed, already current, removed from unmatched scenes, cleared from uniquely matched items with invalid keys, and skipped as ambiguous or invalid. Preserve the existing scene update and merge counts. Include enough scene ID and Plex key information in warnings to investigate conflicts without depending on title matching.

The matched-path join remains authoritative. A stored rating key must not cause reconcile to match a scene whose current files no longer belong to that Plex item. Thus a Plex merge, split, or replacement is corrected by a later full path-based run.

## Lookup contract

Read `custom_fields.plex_rating_key` from `findScene`/`findScenes` when starting from a Stash scene. To start with a Plex rating key, query `findScenes(scene_filter: {custom_fields: [{field: "plex_rating_key", value: ["12345"], modifier: EQUALS}]})`, or use a local index of scene custom fields if the deployed Stash version's custom-field filter behaves differently. More than one scene may legitimately carry the same key until reconcile can merge them; callers must accept a list. Resolve a returned key against the configured Plex server and handle a missing Plex record as stale data pending reconciliation.

Example update input, retaining any other custom fields:

```json
{
  "id": "456",
  "custom_fields": {"partial": {"plex_rating_key": "12345"}}
}
```

verify a uniquely path-matched scene with an invalid key has its old key removed, while ambiguous scenes are untouched and invalid-key scenes are excluded from unmatched-scene cleanup; verify scenes without `plex_rating_key` receive no removal mutation; verify planning creates no metadata entities; verify recovery-artifact failure aborts the per-video apply phase before any resolver or mutation; simulate crashes after merge and after restore, ensuring resume never re-merges deleted source scenes and restores each pending entry idempotently; verify concurrent runs serialize from before Scan/Clean through cleanup and cannot apply stale plans, the active artifact cannot be replaced, and a rerun discovers it without guessing filenames; verify a missing destination quarantines the snapshot while allowing unrelated scenes to proceed and protecting affected IDs from cleanup/merge across later process restarts; verify unresolved quarantine causes full-run Clean to be skipped; verify the ignore rules cover nested quarantine JSON, lock files, and temporary files; verify active recovery precedes Stash Scan/Clean and an unresolved recovery aborts before either; verify the artifact is mode `0600`, uses the configured/checkout/install directory in standalone CLI and mass-process invocation from another working directory, and is removed only after all restores succeed; verify quarantine records are found from a different working directory because the quarantine directory is rooted under the resolved reference directory; benchmark large-library full hydration for `--limit` and `--added-in-last-days` runs and report its progress; and assert that `partial` and `remove` never replace unrelated custom fields. This full hydration is required for global ambiguity validation, while `--path` already reloads the full inventory before filtering in the current command.
- At command startup, before `stash.scan()` or `stash.clean()`, use a read-only schema preflight to verify the scene custom-field output, scene-update input, and `partial`/`remove` operations are supported. If `remove` is unavailable, do not enable stale-key cleanup or invalid-key clearing; keep key reads/writes available where supported and report the limitation clearly. Abort before any scan, Clean, or scene mutation if a required read/write capability is missing; do not discover support by attempting a write.
- Integration check on a test scene: set an unrelated custom field, reconcile it, read both fields back, query by rating key, rerun to confirm idempotence, then test a key change and a full-run orphan cleanup. Verify the merge case with two Stash scenes that become one Plex item, including custom-field union passed through `sceneMerge.values` and readback verification.
- Roll out through the existing `plexadm stash reconcile` call in `scripts/mass_process.sh`; no new mass-process stage is needed. A full reconcile backfills all matched scenes. Update `.gitignore` with explicit entries for `reference/stash-reconcile-merge-recovery.lock`, temporary recovery files, and the recursive `reference/stash-reconcile-merge-quarantine/` directory; the existing `reference/*.json` rule only covers files directly in `reference/`. Update the README's Stash Reconcile section and CLI help when implementation lands. If schema support is missing, fail with a clear version/capability error before mutating scenes.

## Boundaries

The key is not a duplicate detector and does not replace phash or file-path comparison. It is not stable across Plex library rebuilds. Reconcile cannot map files absent from either library, and partial runs cannot establish that an unmatched scene has become orphaned. Custom-field writes are Stash mutations; they should follow existing reconcile error handling and be visible in its progress summary.
