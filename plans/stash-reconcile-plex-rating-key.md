# Design: store the Plex rating key on Stash scenes during reconcile

## Goal

After `plexadm stash reconcile`, a Stash scene that matches a Plex video by file path should expose that video's Plex `ratingKey`. This makes a Stash-to-Plex lookup possible without rescanning and joining both libraries' file paths. A Plex merge should update the surviving Stash scene to the surviving Plex rating key on the next reconcile run.

This document describes the implementation; it does not change reconcile behavior yet.

## Current behavior and supported storage

On current `master`, `plexadm/stash_reconcile.py` optionally scans Stash, then runs Stash Clean only for a full Plex-library run. Runs scoped by `--limit`, `--added-in-last-days`, or `--path` skip Clean because it affects the entire Stash library. Reconcile then indexes scenes by file path and matches Plex video locations to that index. One matched scene receives `sceneUpdate`; multiple matched scenes are combined with `sceneMerge`, with the lowest numeric Stash scene ID as the destination. A Plex video with no usable descriptive metadata is recorded in the scope CSV and receives no Stash metadata update. `plexadm/stash.py` currently requests no scene identifier field that could hold a Plex key.

The running Stash instance reports version `v0.31.1`. Its GraphQL schema exposes `Scene.custom_fields: Map!` and `SceneUpdateInput.custom_fields: CustomFieldsInput`; `CustomFieldsInput.partial` updates only named keys, while `full` replaces the entire map. `SceneFilterType.custom_fields` accepts field criteria, so this field can support a direct Stash query. Check schema support at startup or document `v0.31.1` as the minimum supported Stash version for this feature.

Use a single namespaced custom field, `plex_rating_key`, containing the decimal `ratingKey` as a **string**. Plex IDs identify records within one Plex server, which matches this tool's configured single-server model. The key can change if Plex replaces an item; it is a lookup hint maintained by reconcile, not a permanent identity for the media file. If multiple Plex servers are supported later, add server identity before treating the key as globally unique.

Do not use Stash `stash_ids`: those identify entities on Stash-box endpoints. `code`, `details`, and `urls` have user-facing scene metadata meanings and could overwrite unrelated values. The partial custom-field update preserves other custom fields.

Treat `plex_rating_key` as a field reserved and owned by plexadm. Reconcile may set or remove this one key, but must preserve unrelated custom fields and must never replace the full custom-field map.

## Reconcile flow

1. Keep the existing `_FIND_SCENES` query and `all_scenes()` path-to-scene return contract unchanged for their current callers. Add a reconcile-specific complete-inventory query/method that selects `custom_fields` while retaining the full scene shape the current reconcile loop uses, including `performers` and `tags`, plus file paths. Its collection must retain scenes with `files` equal to `null` or an empty list and must not collapse scenes that share a file path. Build the reconcile path index from this complete collection, preserving every scene associated with a path; do not use the legacy lossy path-to-single-scene map as the cleanup inventory. This keeps sync-tags, backfill-tags, and inventory callers from acquiring a new custom-field schema dependency, and prevents reconciliation from dropping existing performer/tag memberships.
2. After the Plex video list is loaded, perform a read-only planning pass. For partial scopes (`--limit`, `--path`, or `--added-in-last-days`), load the full Plex video inventory for ambiguity validation while using only the selected subset to decide which videos receive the requested reconcile work. Record every path match from the full inventory in a `path_matched_scene_ids` set and record the distinct Plex video items matched to each Stash scene. Give each video a run-local item identity while enumerating it, so an item with a missing or invalid `ratingKey` still counts when detecting ambiguity. A scene matched to more than one Plex item is ambiguous even if only one of those items has a valid key. Report its ID and conflicting item/key details, exclude every planned write and merge involving that scene, and count it separately. If the full inventory cannot be loaded for a partial run, abort before any per-video Stash entity creation or scene mutation rather than treating selected-scope matches as globally unambiguous. Finish matching and ambiguity validation for the entire inventory before creating metadata entities or applying scene changes. This prevents the last item processed from silently winning and ensures ambiguous scenes are not mutated as a side effect of an earlier item.
3. Normalize each selected `video.ratingKey` to a nonempty decimal string before planning a key write. Report and skip key writes for videos with an absent or invalid key, but retain their path matches: preserve any existing key on those scenes during stale-key cleanup. When a video has a unique, non-ambiguous scene match, existing non-key reconciliation may continue under its current metadata rules, while the invalid key itself is not written. Keep the planning pass read-only: do not call `find_or_create_studio`, `find_or_create_performer`, `find_or_create_tag`, or any other mutating resolver while planning. In the apply phase, resolve/create entities only for validated, non-ambiguous planned operations, then perform the corresponding scene update or merge. For an ordinary one-scene match with a valid key, include `custom_fields: {partial: {plex_rating_key: key}}` in the existing `sceneUpdate` input. For a video with no usable descriptive metadata, issue a field-only `sceneUpdate` for **each** matched scene whose key is missing or different; keep those scenes in the existing `matched_no_data` scope count. Avoid an extra field-only call when the stored key already matches. This leaves the current no-metadata merge gate intact, so several Stash scenes can temporarily hold the same Plex key.
4. For a multi-scene match that passes the existing metadata gate, retain the current scene merge. After `sceneMerge` succeeds, set the key on the surviving destination with a separate `sceneUpdate` using `partial`. Keeping this update separate avoids assuming how Stash combines source custom fields during a merge. If this final update fails, surface the error; the next reconcile can repair the destination using its merged file paths.
5. Only after a successful **full** Plex scan and completion of the validated update/merge plan, remove `plex_rating_key` from scenes absent from `path_matched_scene_ids` that currently contain that key, using `custom_fields: {remove: ["plex_rating_key"]}`. Determine path matches independently of key validation: a scene matched to a Plex video with a missing or invalid key is not stale and must retain its existing key. Do not issue a removal mutation for a scene without the key, and count only keys actually removed. Use the complete scene collection for this comparison, including fileless scenes and scenes omitted by a single-value path index; determine path matches without losing scenes that share a path. Do not clear keys on runs limited by `--limit`, `--added-in-last-days`, or `--path`. Never clear unrelated custom fields. On current `master`, a full run performs Stash Clean before building the scene inventory; partial runs skip Clean. This design's stale-key cleanup handles surviving Stash scenes that have no Plex path match.
6. Print counts for keys added, changed, already current, removed from unmatched scenes, and skipped as ambiguous or invalid. Preserve the existing scene update and merge counts. Include enough scene ID and Plex key information in warnings to investigate conflicts without depending on title matching.

The matched-path join remains authoritative. A stored rating key must not cause reconcile to match a scene whose current files no longer belong to that Plex item. Thus a Plex merge, split, or replacement is corrected by a later full path-based run.

## Lookup contract

Read `custom_fields.plex_rating_key` from `findScene`/`findScenes` when starting from a Stash scene. To start with a Plex rating key, query `findScenes(scene_filter: {custom_fields: [{field: "plex_rating_key", value: ["12345"], modifier: EQUALS}]})`, or use a local index of scene custom fields if the deployed Stash version's custom-field filter behaves differently. More than one scene may legitimately carry the same key until reconcile can merge them; callers must accept a list. Resolve a returned key against the configured Plex server and handle a missing Plex record as stale data pending reconciliation.

Example update input, retaining any other custom fields:

```json
{
  "id": "456",
  "custom_fields": {"partial": {"plex_rating_key": "12345"}}
}
```

## Validation and rollout

- Unit coverage: single-scene update, no-metadata match, multi-scene merge followed by key update, unchanged key, changed key after a Plex merge, invalid key, ambiguous scene, partial-run cleanup guard, and full-run stale-key removal. Verify that the legacy query stays unchanged and the reconcile-specific query preserves `performers`, `tags`, fileless scenes, and duplicate paths; cover one valid and one invalid-key Plex item matching the same scene; cover partial-run ambiguity caused by an out-of-scope Plex item; verify a path-matched scene with an invalid key is excluded from cleanup; verify scenes without `plex_rating_key` receive no removal mutation; verify planning creates no metadata entities; and assert that `partial` and `remove` never replace unrelated custom fields.
- At command startup, before `stash.scan()` or `stash.clean()`, use a read-only schema preflight to verify the scene custom-field output, scene-update input, and `partial`/`remove` operations are supported. Abort before any scan, Clean, or scene mutation if a required capability is missing; do not discover support by attempting a write.
- Integration check on a test scene: set an unrelated custom field, reconcile it, read both fields back, query by rating key, rerun to confirm idempotence, then test a key change and a full-run orphan cleanup. Verify the merge case with two Stash scenes that become one Plex item.
- Roll out through the existing `plexadm stash reconcile` call in `scripts/mass_process.sh`; no new mass-process stage is needed. A full reconcile backfills all matched scenes. Update the README's Stash Reconcile section and CLI help when implementation lands. If schema support is missing, fail with a clear version/capability error before mutating scenes.

## Boundaries

The key is not a duplicate detector and does not replace phash or file-path comparison. It is not stable across Plex library rebuilds. Reconcile cannot map files absent from either library, and partial runs cannot establish that an unmatched scene has become orphaned. Custom-field writes are Stash mutations; they should follow existing reconcile error handling and be visible in its progress summary.
